The project

I completed CS50 Finance using the course's Flask distribution code as a starting point. My work connects account registration, stock lookup, buying and selling, a portfolio view, and transaction history, then extends the experience with account and trading shortcuts.

This project brings together the layers of a web application: handling an HTTP request, checking the signed-in user's state, reading and updating relational data, and rendering the result as a page.

APPLICATION FLOW

From an account to a portfolio

  • Register and sign in. Create an account with a unique username and a confirmed password.
  • Look up a symbol. A quote form passes the stock symbol to the quote helper.
  • Buy shares. The route checks the quote and available cash, updates the balance and holdings, and records the purchase.
  • Review holdings. The portfolio lists each stock's share quantity, quoted price, and value, alongside available cash.
  • Sell and review history. Sales update holdings and cash; the history page shows the user's recorded trades.

All trading uses virtual money. The stock quote helper was originally connected to IEX; the source documents that historical dependency rather than offering a live trading demo.

BACKEND

Flask routes and sessions

app.py maps URLs to application behavior. GET requests display forms; POST requests process submitted data. After a completed trade, a redirect returns the user to the portfolio.

The shared login_required decorator guards account-specific routes. A filesystem-backed session stores the user's ID, and queries use that ID to select their account, holdings, and transaction history.

app.py
Routes, account actions, trade processing, and database queries.
helpers.py
Authentication guard, quote lookup, error pages, and USD formatting.
templates/
HTML views receiving data from the Flask routes.

The code uses parameterized queries through cs50.SQL and hashes passwords with Werkzeug. As an early learning project, its validation and trade updates still have room for improvement.

DATA MODEL

Current state and recorded history

Three SQLite tables separate account data, present holdings, and past trades. Each holding and transaction is associated with a user through person_id.

A purchase changes the cash balance and the holding quantity, while also adding a transaction record. The portfolio reads current state; the history page reads the trade records.

FRONTEND

Jinja templates and Bootstrap

The shared layout.html defines the page structure and navigation. Jinja template inheritance keeps that structure consistent across registration, quotes, buying, selling, and history.

The portfolio template loops over holdings to render the table. Bootstrap provides navigation and table styling, while a custom usd filter formats currency values. Flask passes the data into the templates, keeping the interface closely connected to the user's session and database records.

PERSONAL TOUCHES

Extending the core workflow

My submission implements four extensions beyond the core trading pages:

  • Password changes: a signed-in user can set and confirm a new password.
  • Additional virtual cash: an account page adds simulated funds to the balance.
  • Trading from a portfolio row: Buy more and Sell buttons open the relevant form with the stock symbol prefilled.
  • Password rules: registration checks for a minimum of five characters, a digit, and a symbol from the code's allowed set.

These small additions connect account management and trading more directly to the user's portfolio.
